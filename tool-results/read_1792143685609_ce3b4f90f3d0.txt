   706→

   708→2. consult the relevant audit for historical decisions and previously verified state;
   709→3. distinguish an implementation defect from stale documentation;
   710→4. update `AGENTS.md` only when current evidence supports the correction;
   711→5. preserve historical audits and record later corrections explicitly; and
   712→6. stop if resolving the conflict requires a human scope or architecture decision.
   713→
   714→Graphify helps navigate and reduce context usage. It is not evidence that a feature
   715→works and does not override project state.

   747→# 26. Test Execution and Server Lifecycle Policy
   748→
   749→This policy defines when validation runs, how expensive checks are scheduled, and how
   750→local development/production servers are managed. It reduces repeated setup and
   751→browser-test stalls without weakening task completion or phase gates.
   752→
   753→## 25.1 Three-Level Testing Strategy
   754→
   755→Validation is organized into three levels. Select the lowest level that provides
   756→reliable evidence for the change, and run higher levels at the appropriate milestone.
   757→
   758→### Level 1 — Batch Validation
   759→
   760→Run during ordinary implementation batches and after focused changes:
   761→
   762→- typecheck
   763→- lint
   764→- relevant unit tests
   765→- relevant component or integration tests that do not require a persistent server
   766→- content/schema/data validation
   767→- focused deterministic scripts or probes
   768→
   769→Run only checks relevant to the changed code, plus inexpensive required regression
   770→checks. Do not start a production server or browser merely to repeat checks that can
   771→be established locally.
   772→
   773→### Level 2 — Phase Validation
   774→
   775→Run when implementation work for a phase is substantially complete and before
   776→evaluating its Phase Gate:
   777→
   778→- complete project typecheck and lint
   779→- relevant full test suites
   780→- content and route validation
   781→- production build
   782→- static output and generated-route checks
   783→- focused integration checks required by that phase
   784→
   785→A production build is not proof that browser behavior, responsive layout, or
   786→accessibility has been verified.
   787→
   788→### Level 3 — Final Quality Gate
   789→
   790→Run expensive or environment-dependent checks at the appropriate phase gate,
   791→not repeatedly after every small implementation batch:
   792→
   793→- production-server smoke tests for required routes and critical flows
   794→- browser E2E tests and real interaction checks
   795→- desktop, tablet, and mobile responsive verification
   796→- keyboard, focus, semantic, and accessibility checks
   797→- runtime console/error checks
   798→- bilingual Persian RTL and English LTR checks when required by the phase
   799→
   800→The phase-specific task list and Quality Gates determine which checks are mandatory.
   801→Deferring a check changes its execution time; it does not remove the requirement.
   802→
   803→## 25.2 Batch Validation Rules
   804→
   805→1. After a focused code change, run the smallest relevant deterministic checks.
   806→2. When related tasks are implemented together, validate them as one coherent batch
   807→   rather than repeating the same setup and test suite after every subtask.
   808→3. Re-run checks affected by subsequent code changes. Do not rerun unrelated checks
   809→   without a reason.
   810→4. Record exactly which checks ran and their results.
   811→5. A skipped, deferred, unavailable, or unrun check must never be reported as PASS.
   812→
   813→## 25.3 Phase Validation Rules
   814→
   815→1. Before declaring a phase ready for its gate, run the Level 2 checks required by
   816→   that phase.
   817→2. Run Level 3 checks once at the phase gate when those checks are required by the
   818→   phase tasks or gate.
   819→3. If a change after validation affects validated behavior, repeat the relevant
   820→   check before relying on the earlier result.
   821→4. Do not create the phase audit or mark the phase complete until every mandatory
   822→   task and gate condition has evidence.
   823→5. If a mandatory check cannot be completed, keep the task/phase incomplete and
   824→   report the exact deferred or blocked check.
   825→
   826→## 25.4 Final Quality Gate Requirements
   827→
   828→The final quality gate is a consolidated verification point, not a reason to waive
   829→earlier task-level validation.
   830→
   831→At the relevant phase gate:
   832→
   833→- execute required browser, responsive, accessibility, and runtime checks as a
   834→  consolidated pass;
   835→- verify the critical user journey and all routes/flows required by the phase;
   836→- include both Persian RTL and English LTR wherever the bilingual requirement applies;
   837→- record environment, commands, coverage, results, and limitations;
   838→- resolve failures or leave the corresponding task and phase incomplete.
   839→
   840→Do not claim visual, responsive, browser-interaction, or accessibility success from
   841→typecheck, lint, build, static HTML inspection, or HTTP status alone.
   842→
   843→## 25.5 Server Lifecycle Management
   844→
   845→1. Prefer checks that do not require a persistent server.
   846→2. If a server is required, first inspect whether a suitable server is already running
   847→   and whether it serves the current build/source state.
   848→3. Reuse a healthy server. Do not start duplicate servers or restart a healthy server
   849→   without a concrete reason.
   850→4. When source changes invalidate the running build, stop only the known
   851→   project-owned process and start one replacement using the repository's documented
   852→   command.
   853→5. Start long-running processes so the agent can continue working; use bounded
   854→   readiness polling and bounded request timeouts.
   855→6. Record the process identifier, port, and base URL when useful for handoff.
   856→7. Stop only processes positively identified as belonging to this project. Never
   857→   terminate unrelated processes.
   858→
   859→## 25.6 Failure and Recovery Policy
   860→
   861→If a server, browser, or test command stalls or fails:
   862→
   863→1. Capture available error/output and identify whether the failure is in the code,
   864→   test, browser, server, or environment.
   865→2. Make at most one bounded recovery attempt for the same environmental failure
   866→   (for example, one controlled server restart or one browser relaunch).
   867→3. Do not repeat unbounded polling, restart loops, or identical commands that have
   868→   already failed without new evidence.
   869→4. If recovery fails, stop troubleshooting that environment and continue with
   870→   independent work that can be validated reliably.
   871→5. Mark the affected check as `DEFERRED`, `BLOCKED`, or `NOT VERIFIED`, with a short
   872→   reason and the evidence already obtained.
   873→6. Do not convert an unavailable test into a pass, and do not bypass a mandatory
   874→   gate. Resume the deferred check at the next appropriate gate or when the
   875→   environment is available.
   876→
   877→## 25.7 Reporting and Gate Integrity
   878→
   879→Every validation handoff must distinguish:
   880→
   881→- `PASS` — the check ran and passed;
   882→- `FAIL` — the check ran and failed;
   883→- `DEFERRED` — intentionally postponed to the appropriate gate;
   884→- `BLOCKED` — attempted but prevented by a stated blocker;
   885→- `NOT RUN` — not attempted.
   886→
   887→Report the commands or test method, scope/coverage, result, and relevant limitations.
   888→State whether browser-based visual verification actually ran.
   889→
   890→A task may be marked complete only when its required validation has passed. A phase
   891→may be marked complete, its audit created, and its status advanced only when all
   892→phase tasks and mandatory gate checks have passed. Deferred checks remain open.
   893→This policy changes test scheduling and server handling only; it does not reduce
   894→the project's Definition of Done, Quality Gates, phase scope, or release requirements.
